# Dory native candidate

This candidate uses the official NVIDIA Q5_K_M GGUF and the Dory llama.cpp PR.
The source is staged. The binary is not built. The weights are not downloaded.
No server or benchmark has run for this candidate.

- Source: `brianchmielNV/llama.cpp`, commit
  `43e865ec059a35d57f1167eaea76ca187077f063`.
- Upstream change: <https://github.com/ggml-org/llama.cpp/pull/30306>.
- Official model: `nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-GGUF`, revision
  `0963c8000791e77b2b1b49aa387d92a6da9988d6`.
- Model file: `NVIDIA-Nemotron-Labs-Dory1.0-4B-Q5_K_M.gguf`.
- Model size: `3673288864` bytes.
- Model SHA256:
  `96080be49ffd67b916018b7bdef8c484762576fb52780e10ab98ac4978a660e0`.

`manifest.json` contains the archive checksum, build options, paths, and settings.
`source-files.sha256` records every staged source file. Check these hashes before
the build. These hashes detect later changes. They do not prove that the source
is safe. `model-metadata.json` and `model-card.md` retain the official file metadata
and model instructions. The model file must pass its size and SHA256 checks before
use.

The source is under `state/sources/dory-native/43e865ec059a35d57f1167eaea76ca187077f063`.
The future binary is `state/builds/dory-native/bin/llama-server`.

## Deferred build

Verify the staged source without network access:

```sh
uv run --no-project --python .venv/bin/python python experiments/dory-native/prepare.py
```

If the source is missing, add `--fetch`. The helper reuses a verified archive
when available. It downloads only a missing pinned source archive. It checks
the archive size and SHA256 before extraction. It refuses changed source files,
extra files, symbolic links, and unsafe archive paths. It does not fetch weights,
build code, start a server, or run benchmarks.

Use the generic native build helper with `manifest.json`. Keep its plan mode
until the machine is free. The recipe selects the existing private CUDA 13
toolkit and Ada compute capability 8.9. It builds only `llama-server` with two
compiler jobs. Use heavy-management with a 16 GiB memory cap, no swap, and a
90-minute time cap. Check the effective cgroup limits when the build starts.
Do not change queue concurrency.

`LLAMA_BUILD_TOOLS` must stay enabled because this source adds the server through
the tools directory. Building the `llama-server` target does not build each tool.
The recipe disables UI downloads, external LLGuidance builds, RPC, HTTPS support,
and native subprocess support. CUDA CCCL uses the installed toolkit headers.
The build has not validated these options yet.

## Server settings

Use loopback only, one slot, 262144 context tokens, Q8_0 K and V caches, flash
attention, 999 GPU layers, and disabled automatic memory fitting. Enable GPU KV
and operation placement. Load the verified local model with `--offline` and
`--load-mode none`. Do not enable the server's built-in tools or MCP proxy.
OpenCode supplies its own tool schemas and runs its own approved tools.

Select loop count 1, 2, or 4 with:

```text
--override-kv dory.num_loops=int:2,dory.recurrent_kv_cache_mode=str:last_loop
```

The source uses names such as `blk.0.residual_alpha.weight` and
`blk.0.attn_qk_scale.weight`. The report's `blk.(scale|alpha).` expression does
not match these names. The prepared expression is:

```text
^blk\.[0-9]+\.(residual_alpha|attn_qk_scale|attn_gate_scale|ffn_gate_scale|ffn_up_scale)\.weight$=CUDA0,^output_scale\.weight$=CUDA0,^token_embd\.weight$=CUDA0
```

Pass this as one `--override-tensor` argument. `static-check.json` records checks
against the names generated by the pinned source. The actual GGUF names and
loader placement still need inspection after the download. Startup logs must
confirm GPU residency. Windows can still change GPU memory residency outside
llama.cpp.

For OpenCode, enable Jinja and reasoning. Set:

```text
--chat-template-kwargs {"force_nonempty_content":true}
```

This is the coding-agent setting from NVIDIA's model card. Tool parsing,
message content, and a full OpenCode round still require a runtime check.

The report used batch 2048, ubatch 1024, one CPU thread, and `--cache-ram 0`.
Retain these settings in a separate reproduction case. RAM prompt snapshots are
a different experiment. The reported sampling settings are in `manifest.json`.

## Constraints and review

The PR is open and marked as a draft. Its author reports that long-context
qualification is incomplete. Context shifting is unsupported, so use
`--no-context-shift`. OpenCode must compact before the context limit. Verify that
compaction produces a valid new prompt and that later tool calls still work.
Do not promise infinite-context server behavior.

`last_loop` keeps historical tokens' final-loop KV. It changes predictions from
`per_loop`. Prefill chunk size also changes predictions in this mode. Record
both batch sizes in every result. Do not compare quality across different
chunk sizes without recording that difference. Loop counts above four and
runtime model re-save are unsupported.

The review covered all 17 PR file diffs, the Dory graph and converter, tensor
override parsing, and relevant build options. The added code implements model
metadata, tensors, graph operations, cache placement, quantization rules, and
tests. The reviewed changes add no networking, subprocess execution, telemetry,
URL fetches, or tool execution. This is a bounded review. It is not a full audit
of llama.cpp or a proof of memory safety.

The official SHA256 check establishes file identity. Q5_K_M changes numerical
weights through quantization. It cannot establish equality to BF16. No weight
comparison or runtime validation was performed during preparation.

The quoted 50 tok/s decode and 1580 tok/s prefill remain external results. The
reported 256K setting does not establish the occupied context at measurement.
Measure actual input tokens, generation, tool calls, compaction, prefill chunk
sizes, GPU memory, and CPU/RAM use when benchmarks are authorized.
